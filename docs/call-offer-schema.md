# WhatsApp Call Offer Schema (Signaling Phase)

This document describes the outbound `offer` stanza structure used by the whatsmeow call signaling layer.
It is based on analysis of baileys-caller, go-whatsapp/whatsmeow, inbound `CallOffer` captures, and whatsmeow-calls.

## Stanza envelope

```xml
<call id="{stanzaId}" from="{ownJID}" to="{routeDeviceJID}">
  <offer call-id="..." call-creator="{ownLID}" platform="web" version="...">
    ...
  </offer>
</call>
```

## Inner offer node

### Required attributes

| Attribute | Description |
|-----------|-------------|
| `call-id` | 32-char hex ID (`00` + 30 uppercase hex chars) |
| `call-creator` | Caller LID (`@lid`) |

### Optional attributes

| Attribute | Description |
|-----------|-------------|
| `platform` | Caller platform (e.g. `web`) |
| `version` | Client version string |

### Required children (audio call)

| Tag | Attributes | Purpose |
|-----|------------|---------|
| `audio` | `enc=opus`, `rate=16000` | Primary codec |
| `audio` | `enc=opus`, `rate=8000` | Fallback codec |
| `capability` | `ver=1` | 6-byte capability blob |
| `destination` | — | Per-device encrypted callKey |
| `encopt` | `keygen=2` | Encryption options |
| `net` | `medium=3` | Network medium |
| `voip_settings` | `uncompressed=1` | JSON VoIP options |

### Audio codec children

```xml
<audio enc="opus" rate="16000"/>
<audio enc="opus" rate="8000"/>
```

### Capability child

```xml
<capability ver="1">0104f70bce03</capability>
```

Bytes: `{1, 4, 247, 11, 206, 3}`

### VoIP settings child

```xml
<voip_settings uncompressed="1">{"encode":{"codec":"opus"},"options":{"disable_p2p":"1"}}</voip_settings>
```

### Multi-device destination

When calling a peer, encrypt the call key for each target device (peer + own linked devices):

```xml
<destination>
  <to jid="{deviceJID}">
    <enc v="2" count="0">{rawCallKey}</enc>
  </to>
</destination>
```

There must be **no** root-level `enc` child when `destination` is present.

Each `enc` child is replaced with Signal-encrypted `waE2E.Message{call:{callKey}}` before sending.

### Relay node (media phase)

Real offers from WhatsApp Web also include a `relay` child with tokens, keys, and edge endpoints.
That data is generated by the official VoIP WASM stack after the server ack. The current Go-only
signaling layer omits relay; ringing may work without it, but media transport requires relay binding.

## callKey encryption

1. Generate 32 random bytes as `callKey`
2. Marshal `waE2E.Message{Call: &waE2E.Call{CallKey: key}}`
3. Encrypt with Signal session per target device in `destination`
4. Replace each `enc` content with ciphertext; set `type=pkmsg|msg`

Prefer established Signal sessions (`type=msg`) over pre-key (`type=pkmsg`) when possible;
some servers drop offers encrypted only with pre-keys on linked devices.

## Server ack

After sending the `<call>` stanza, the server returns an `<ack>` with matching `id`.
The media WASM stack feeds this ack back to receive relay-list updates (future media phase).

## Capturing real offers

Use `cmd/call-dump` to log inbound call nodes:

```bash
go run ./cmd/call-dump
```

Or dump from code:

```go
data, _ := whatsmeow.DumpCallNode(evt.Data)
```
